01 Dữ liệu Reflected được đưa vào HTML ở đâu?

Tham số q được truyền vào template tại vùng kết quả tìm kiếm; bản lỗi dùng Markup(q) nên trở thành markup.

02 Ứng dụng có escape <, >, ", ' không?

Vulnerable không escape vì Markup đánh dấu trusted; secure để Jinja autoescape thành &lt;, &gt;, &quot;, &#39;.

03 Nạn nhân bấm URL chứa payload thì sao?

Server phản chiếu payload; browser parse response và event handler chạy trong origin của ứng dụng.

04 Vì sao Stored nguy hiểm hơn Reflected?

Payload tồn tại trong DB và tự phát lại cho nhiều lần xem, không cần nạn nhân mở đúng URL payload.

05 Stored ảnh hưởng mọi người xem trang không?

Có, nếu họ nhận cùng HTML chứa payload; phạm vi phụ thuộc quyền xem bài viết.

06 Cookie không HttpOnly có rủi ro gì?

JavaScript do XSS có thể đọc cookie không HttpOnly và gửi ra ngoài; HttpOnly giảm hậu quả đánh cắp phiên.

07 Vì sao DOM XSS xảy ra ở browser?

Fragment không gửi tới server; JavaScript client đọc location.hash rồi đưa trực tiếp vào innerHTML.

08 So sánh Reflected, Stored và DOM XSS?

Reflected theo request hiện tại; Stored lưu server rồi phát lại; DOM là source→sink ở client.

09 Vì sao validate input chưa đủ?

Input hợp lệ nghiệp vụ vẫn có thể nguy hiểm ở ngữ cảnh HTML/attribute/URL/JS; phải xử lý đúng sink.

10 Vì sao cần output encoding?

Encoding biến ký tự cú pháp thành dữ liệu, ngăn browser tạo node hoặc script.

11 CSP có thay thế sửa code không?

Không. CSP là defense in depth; sink nguy hiểm vẫn phải sửa.

12 Vá từng lỗi thế nào?

Reflected: autoescape; Stored: sanitize allowlist; DOM: textContent; thêm CSP và cookie flags.

HTML/attribute/URL/JS encoding · Sanitization allowlist · textContent · CSP · HttpOnly · Secure · SameSite · Không tin URL/form/cookie/localStorage

01 Chương trình crash ở đâu?

ASan báo stack-buffer-overflow tại strcpy trong process_name() của vulnerable_processor.c.

02 Stack có bị ghi đè không?

Có. WRITE size 33/65 đi qua ranh giới name[32]; ASan dừng tiến trình trước khi lan xa.

03 Độ dài nào bắt đầu gây lỗi?

31 byte + NUL vừa đủ; 32 byte cần 33 byte nên bắt đầu overflow trong evidence của lab.

04 Buffer nằm ở vùng nhớ nào?

name[32] là biến cục bộ trong stack frame của process_name().

05 Input vượt kích thước gây gì?

Ghi đè byte kế tiếp, có thể phá canary, frame pointer, return address và gây crash/corruption.

06 Vì sao strcpy/gets/sprintf nguy hiểm?

Chúng không tự biết capacity đích hoặc dễ dùng thiếu giới hạn/kiểm tra truncation.

07 Vì sao memory corruption nghiêm trọng?

Nó có thể phá dữ liệu và luồng điều khiển, nghiêm trọng hơn sai quyết định logic đơn thuần.

08 Canary, ASLR, DEP/NX có tác dụng gì?

Canary phát hiện ghi đè; ASLR ngẫu nhiên địa chỉ; NX cấm thực thi vùng dữ liệu.

09 Buffer Overflow khác Injection?

Overflow phá an toàn bộ nhớ; injection làm input thành cú pháp của interpreter.

10 Vì sao backend native bị kích hoạt qua HTTP?

Request đi qua Flask/subprocess và trở thành argv cho hàm C vulnerable.

11 Vì sao firewall không đủ?

Request hợp lệ về HTTP và đúng route; lỗi xuất hiện sau khi dữ liệu vào code native.

12 Bản vá hiệu quả vì sao?

Length patch và snprintf đều giữ tối đa 31 byte, kiểm tra lỗi/truncation trước khi dùng buffer.

13 Ít nhất 3 hardening?

Stack protector, ASLR, NX/DEP; bổ sung PIE và RELRO, giới hạn request và ưu tiên memory-safe language.

CSRF mượn quyền gửi request; XSS mượn quyền chạy code

VICTIM LOGIN :5004→ATTACKER PAGE :9004→BROWSER + COOKIE→POST CHANGE EMAIL→SERVER MUTATES

Cơ chế CSRF

/ Victim đã login ở 127.0.0.1:5004.

/ Attacker page ở 127.0.0.1:9004.

/ Browser tự gửi cookie phù hợp.

XSS vs CSRF

/ XSS: chèn code vào origin nạn nhân; có thể đọc DOM/response.

/ CSRF: ép browser gửi request; thường không đọc được response.

/ XSS lợi dụng trust vào content; CSRF lợi dụng ambient authority.

Integrity/authenticity; không che nội dung, không tự revoke và không tự phân quyền.
